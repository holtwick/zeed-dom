# 🚦 Performance

zeed-dom is a small, pragmatic DOM. It does not parse HTML by the WHATWG specification, which is a big part of why it is fast. This page compares it to other DOM implementations for Node.js and Bun, lists the guarantees it gives for hostile input, and its limits.

All numbers on this page are the output of [test/compare-bench.ts](test/compare-bench.ts), see [How to run](#how-to-run) to reproduce them on your machine.

How to read it:

- **Parsing** is where zeed-dom is fastest. The other libraries parse by the specification (implied end tags, foster parenting, and so on), so the comparison is not entirely fair: zeed-dom does less work and gives a less exact tree for broken HTML.
- **Building trees, ProseMirror and tiptap** (`generateHTML` and `generateJSON` on the server) are on par with or faster than the alternatives.
- **Serializing and `querySelectorAll`** are on par with the fastest of the other libraries.

The pages are the HTML files in [`files/`](files/). The ProseMirror document uses `prosemirror-schema-basic`, with bold text and a link in every paragraph; the parse result is checked against the original document.

## Hostile input

Servers often parse HTML or render documents that come from users. The work is synchronous, so a slow input blocks the event loop. zeed-dom keeps the following in linear time or bounded:

- **Parsing** is linear in the length of the input, whatever it contains. The tokenizer scans once from left to right and does not use backtracking regular expressions. Unclosed tags, comments, quotes, `<script>` and `<style>` elements and stray end tags cannot make it slow.
- **Nesting depth** of parsed elements is limited to 512 (`MAX_PARSE_DEPTH`), the same limit as Chrome's HTML parser. Deeper elements become siblings at that depth, so deeply nested input cannot overflow the call stack.
- **Tree walks** (`render`, `outerHTML`, `textContent`, `querySelector`, `querySelectorAll`, `cloneNode`, `contains`) are iterative and work for trees of any depth built in code.
- **`appendChild`, `nextSibling` and `previousSibling`** are O(1). Each node keeps its position in the parent as a hint, which is repaired on demand after other mutations.
- **`:first-child`, `:last-child` and `:nth-child`** only look at the neighbouring siblings.
- **`querySelector`, `getElementById`, `document.body` and `document.head`** stop at the first match.

Before these fixes, several of the inputs below took seconds to minutes in zeed-dom or overflowed the call stack, see [issue #18](https://github.com/holtwick/zeed-dom/issues/18) and the commits after it.

## Limits

- **Inserting or removing at the front** of a parent with very many children (`insertBefore(x, parent.firstChild)`, `removeChild(parent.firstChild)`) is O(n) per call, because children are stored in an array. It is fast in practice because only the array items move, but a linked list would be needed to make it O(1).
- **Mutating while walking the siblings** of a parent with very many children, like removing some children in a `nextSibling` loop, is O(n) per mutation: the next sibling lookup after a mutation re-indexes all siblings once. `tidyDOM` does this too. It only matters for thousands of siblings; ProseMirror and tiptap only append or only read and are not affected.
- **Inserting a node into itself or one of its descendants** is ignored with a warning, the DOM throws a `HierarchyRequestError` instead. The check walks up from the parent, so `appendChild` and `insertBefore` of a node with children are O(depth).
- **The serializers** `serializeMarkdown`, `serializePlaintext` and `serializeSafeHTML` are recursive. With parsed input they are safe thanks to the depth limit. Trees nested thousands of levels deep that are built in code can still overflow the call stack there.
- **CSS combinators** like `a b` and `a ~ b` walk the ancestors or previous siblings for each candidate element, as in other simple selector engines.

## How to run

The comparison libraries are only dev dependencies of the [`test/`](test/) folder and are not part of the package. Install them once, then run the benchmark from the project root:

```sh
cd test && npm install --no-package-lock && cd ..
npm run perf:compare               # print the tables
npm run perf:compare -- --write    # update this page and the README
```

The benchmark runs on Node.js and, if it is installed, on Bun. Every combination of runtime and library runs in its own process. Options:

- `--runs=5` takes the best of 5 runs instead of 3.
- `--only=zeed-dom,linkedom` compares only some libraries.
- `--runtimes=node` or `--runtimes=bun` runs only on one runtime.

Other benchmarks:

- `npm run perf:files` parses the pages in `files/` with zeed-dom.
- `npm run perf:parser` measures the tokenizer alone.

The tests in `src/*.spec.ts` contain timing checks for the hostile cases, so a regression to quadratic time fails the test suite.
